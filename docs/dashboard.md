# 이벤트 → 대시보드 (scripts/market_collection/dashboard)

이벤트 엔진 출력(`data/market_collection/events/events.json`)을 팀 대시보드 페이지 한 장(`index.html`)으로 만든다. 같은 폴더의 `report.json`·`continuity.json`·`state.json`은 있으면 상태 배너, 수집 run 목록, 단가 추이에 쓴다. 입력은 수정하지 않고 네트워크도 쓰지 않으며, 결과는 외부 파일 없이 file://로 열린다. 화면은 박건 결정(2026-10-20, "이 형태로 만들어")에 따라 `렛서_대시보드_사용자뷰_1011.html`의 형태를 쓴다(v14 카드 형태는 쓰지 않는다). 왼쪽 변화 목록 박스에는 높이 제한(2026-10-21 박건 요청, 아래 "목록 박스 높이")과 유형 칩·"오늘 이후만" 필터(2026-10-22 박건 요청, 아래 "목록 필터")를 더했다. 일일 workflow가 페이지를 만들어 GitHub Pages(https://letsur-creai-it.github.io/LETSUR/)에 올린다. 저장소가 공개라 이 페이지도 로그인 없이 누구나 열 수 있다. 알림은 이번 범위가 아니다.

## 실행

```sh
python3 -B -m scripts.market_collection.dashboard --root data/market_collection --output dashboard-site
```

- `--output`은 아직 없는 경로여야 한다(있으면 아무것도 쓰지 않고 exit 2). 결과는 `<output>/index.html` 한 파일이다.
- `--internal-routes <파일>`(선택): 렛서가 모델마다 쓰는 공급 경로 파일. 주면 카드의 렛서 관계와 모델별 사용 경로(`MODELS`의 `use`, 지금 화면에는 나오지 않음)를 이 파일로 정하고, 빼면 모든 카드가 "사용 경로 확인 필요"다(아래 "렛서 관계"). workflow는 `samples/market_collection/demo_internal_routes.json`을 넘긴다(2026-10-28부터 레코드마다 근거가 있어 시연용 가정이 아니다. 파일 이름은 그대로 뒀다).
- 종료 코드: 0 정상(입력 문제로 실패 화면을 쓴 경우, 경로 파일을 쓰지 못해 경고를 붙인 경우 포함), 1 예기치 못한 오류(이때도 실패 화면은 쓴다), 2 출력 경로가 이미 있음.
- 기준일(D-day, 캘린더의 오늘)은 생성 시점의 KST 날짜다. 주소 뒤에 `?base=2026-10-12`를 붙이면 그 날짜로 바꿔 볼 수 있다(원본 템플릿 기능). 변화 목록의 날짜 필터도 이 기준일을 쓴다(2026-10-27 결정, 아래 "목록 필터").

### 목록 박스 높이

2026-10-21 박건 요청. 실제 누적 데이터(10-21 run, 이벤트 253건)로 만들면 카드가 61장이라 1024×768 창에서 목록이 3,755px까지 길어지고, 오른쪽 상세(약 1,430px)는 위에 붙은 채 아래가 비었다.

- 값: `.list`를 세로 flex로 두고 `max-height: max(480px, 72vh)`를 준다. 머리(`.lhead`, "전체 변화 · 급한 순")는 박스 위에 남고 `#queue`만 `overflow-y: auto`로 스크롤한다(`min-height: 0`이 있어야 flex 항목이 줄어든다).
- 72vh: 박스 위에서 휠을 굴리면 목록이 먼저 스크롤되므로, 창의 약 28%를 박스 밖에 남겨 페이지를 스크롤할 자리로 둔다. 1024×768 창에서 박스는 553px이고 카드 약 7장이 보인다.
- 480px: 창 높이가 약 667px(480 ÷ 0.72)보다 낮을 때 적용돼 카드 약 6장을 남긴다.
- 1열 화면(940px 이하)에도 같은 값이 걸린다. 카드가 적어 내용이 박스보다 짧으면 높이는 이전과 같고 스크롤도 없다.
- 포커스 테두리: 스크롤 영역은 밖으로 나간 그림을 자르므로 `#queue`를 좌우·아래로 4px 넓히고(음수 margin) 같은 만큼 padding을 줬다. 카드 위치는 그대로이고 키보드 포커스 테두리(`outline` 2px, `outline-offset` 2px)가 잘리지 않는다.
- 선택 카드 보이기(`showSel()`): 기존 `scrollIntoView`는 상세(`#detail`)만 창 위로 올리고 목록은 움직이지 않아, 박스만 두면 칩으로 고른 카드가 박스 밖에 가려질 수 있다. 카드에 `scrollIntoView`를 쓰면 창까지 움직여 상세 이동과 겹치므로, 선택 카드가 박스 밖에 있을 때 `#queue`의 scrollTop만 바꿔 박스 가운데쯤 보인다.
  - 캘린더·일정 칩으로 고를 때, 1열 화면에서 목록 카드를 누를 때, 주소의 `#카드id`로 열 때 맞춘다. 창은 기존대로 상세로 이동한다.
  - 2열 화면에서 목록 카드를 누르면 목록 위치와 창은 그대로다.

### 목록 필터

2026-10-22 박건 요청: "웹의 전체 변화에서 7개 이벤트 카테고리별로 토글할 수 있으면 좋겠어. 지금 너무 많아. 그리고 기본적으론 오늘 날짜 이후의 메시지만 뜨면 좋겠어." 왼쪽 "전체 변화" 목록(`#queue`)만 거른다. 상단 요약, 캘린더, 일정, 상세, 단가 추이는 거르지 않는다(아래 "한계").

- 유형 칩: 목록 머리 밑에 7유형(가격 변경, 예정 변경, 한시 할인, 조건 변경, 모델 출시, 제공 종료, 공급 경로 변경)을 칩으로 두고, "유형 미정" 카드가 있을 때만 "유형 미정" 칩을 하나 더 둔다. 처음에는 아무 칩도 눌리지 않아 모든 유형이 보인다. 칩을 누르면 그 유형만 보이고, 다른 칩을 더 누르면 그 유형도 함께 보인다. 눌린 칩을 다시 누르면 빠지고, 하나도 남지 않으면 전체로 돌아간다(2026-10-27 박건 요청: "버튼을 누르면 해당 버튼에 해당되는 알림만 필터링"). 10/22에는 칩을 누르면 그 유형을 숨겼다.
  - 칩의 숫자는 날짜 필터만 적용한 건수다. 칩을 눌러도 숫자는 그대로이고, 건수가 0인 칩은 흐리게 보이지만 누를 수 있다.
- 날짜 필터(2026-10-27 결정 19절): 카드 날짜(`cd`)가 기준일을 포함한 최근 7일(`PAST_DAYS`) 안이거나 그 뒤인 카드만 보인다. 하루 늦게 본 사람도 처리하지 않은 변화를 놓치지 않게 7일을 남긴다. 이벤트 2건 이상을 묶은 카드는 `cd`와 마지막 관측일(`ld`) 중 늦은 날로 본다. "지난 변화 보기"(처음에는 꺼짐)를 켜면 전부 보인다.
  - 꺼져 있으면 "지난 변화 N건 숨김"을 보인다. N은 유형 칩으로 고른 유형 안에서 센다.
  - 보일 카드가 0장이면 "최근 7일과 앞으로의 변화 0건"과 토글을 함께 보인다. 유형 칩을 누른 상태면 앞에 "선택한 유형의 "가 붙는다.
  - 날짜(`cd`, `ld`)가 하나도 없는 카드는 지난 변화로 센다. build.py가 아래 "유형과 표시 문구"의 순서로 `cd`를 채우므로 실제 데이터에서는 거의 없다.
  - 묶음 카드의 `cd`는 대표 이벤트 하나의 날짜인데, 같은 묶음에는 첫 카드로부터 3일 안(`GROUP_WINDOW_DAYS`)에 관측된 이벤트도 들어온다. 대표보다 늦게 관측된 구성원이 있어도 카드가 `cd`만으로 숨지 않도록 `cd`와 `ld` 중 늦은 날로 센다. `ld`가 없는 카드는 `cd`만 본다.
- 두 필터는 AND로 합친다. 목록 머리의 "전체 변화 N"은 지금 보이는 카드 수다.
- 기준일: 페이지 생성 시점의 KST 날짜(`TODAY`)이고, `?base=`가 있으면 그 날짜다. D-day·캘린더와 같은 날이라 자정 무렵에도 어긋나지 않는다.
- 칩·토글 상태는 저장하지 않는다(주소, localStorage 모두 쓰지 않음). 새로고침하면 처음(모두 켬, 지난 변화 숨김)으로 돌아간다.
- 만드는 쪽: build.py가 카드마다 `kind`(칩 이름)와 `cd`(필터 날짜)를, 묶음 카드에는 `ld`(마지막 관측일)를 내보내고 거르기는 템플릿 JS가 한다. 카드 묶음과 정렬은 그대로다. `kind`, `cd`, `ld`의 규칙은 아래 "유형과 표시 문구"에 있다.
- 선택은 필터와 무관하다. 주소의 `#카드id`, 캘린더 칩, 일정 칩으로 숨겨진 카드를 골라도 상세에는 그 카드가 나오고 필터는 바뀌지 않는다. 목록에는 그 줄이 없어 강조 줄도 없고, "지난 변화 보기"를 켜면 그 줄이 강조된다. 처음 선택은 보이는 카드 중 가장 급한 카드이고, 보이는 카드가 없으면 전체 카드 중 가장 급한 카드다.
- 칩과 토글은 처음에 한 번 만들고 눌림 상태(`aria-pressed`)와 숫자만 고쳐서 누른 뒤에도 포커스가 남는다(Tab으로 이동, Space·Enter로 켜고 끈다). 누르면 목록은 맨 위로 돌아간다.

## 매핑 (events.json → 페이지 데이터)

엔진이 쓴 사실만 옮긴다. 엔진이 만들지 않는 판단은 지어내지 않고 비우거나 평가 보류(`act: "pending"`)로 둔다. 규칙은 박건 승인(2026-10-20)을 따르고 코드는 `build.py`에 있다.

### 카드 묶음과 순서

- OpenRouter 엔드포인트 할인 신호(근거 위치가 엔드포인트 API의 `pricing.discount`인 한시 할인)는 카드로 만들지 않는다(2026-10-27 결정, `endpoint_discount()`). 시작일·종료일·이전 가격이 없고 할인율이 날마다 바뀌어 '할인 · 종료일 미확인' 카드만 쌓였다(10/27 12장). 오늘의 할인율은 공급사 비교 표 그 엔드포인트 행의 비고('할인 N% · 기간 미공지')에 나온다. 이벤트 기록(events.json)에는 그대로 있다. 채널 공지에서 온 할인은 그대로 카드다.

- 이벤트 여러 건이 카드 1장이 될 수 있다. 묶음 키는 모델 + 경로 + 유형 + 하위 태그 + 날짜다.
  - 날짜: 적용일·종료일·제공일(`dates.effective_from`, `dates.end_date`, `period_end.date`, `dates.route_added_date`), 없으면 공지 게시일(`dates.published`의 날짜, UTC), 없으면 관측일(KST).
  - `group_key`가 있으면 `group_key` + 경로로 묶고, `group_role`이 `representative`인 이벤트를 대표로 쓴다.
  - 경로 없는 카드(가격 추적 사이트 글 같은 단서)는 같은 `group_key`의 경로 카드가 하나뿐이고 두 카드의 날짜(카드 날짜, 없으면 피드 글 게시일)가 3일(`GROUP_WINDOW_DAYS`) 안이면 그 경로 카드에 들어가 근거가 된다(`merge_notes`, 2026-10-27 결정 26-3). 이때 대표는 경로가 있는 구성원 중에서 고른다. 날짜를 지키는 까닭은, 엔진이 날짜 없이 받은 옛 피드 글을 두 달 뒤 관측 변화와 한 묶음으로 엮은 경우가 있어서다(예: 8/16 글과 10/17 관측). 10/27 데이터에서는 GPT-5.6 Luna·Terra 글 2장이 Vercel 7/30 공지 카드에 들어갔다.
- 카드 id는 `g_` + 묶음 키 SHA256 앞 12자리다. `ID`에 카드별 원래 `event_id` 목록을 둔다.
- `EVENTS`는 날짜·모델·경로·유형 순으로 넣고, 화면 정렬은 템플릿 규칙을 따른다.

### 유형과 표시 문구

- `t7`: `price_change` 가격 변경, `scheduled_change` 예정 변경, `limited_discount` 한시 할인, `condition_change` 조건 변경, `condition_price_change` 조건·가격 변경(PR #21 박건 결정 2026-10-23, 엔진 반영 전이라 페이지만 준비), `model_release` 모델 출시, `model_end` 제공 종료, `route_change` 공급 경로 변경.
- 유형 미정(`event_type` null)
  - `type_candidates`가 `[model_release, route_change]`이면 공급 경로 변경 · 경로 추가로 둔다(박건 결정 2026-10-20).
  - 그 밖의 미정은 `t7` null이다.
- `kind`(목록 필터의 유형 칩 이름): `t7`이 아니라 이벤트 `event_type`으로 정한다. 7유형 중 하나면 그 이름이고, 아니면(null 포함) "유형 미정"이다. 그래서 위 `[model_release, route_change]` 미정 카드는 `t7`이 "공급 경로 변경"이어도 `kind`는 "유형 미정"이다(목록 묶음 제목은 "모델·경로 변경", 칩은 "유형 미정"). `t7`이 null인 미정 카드는 묶음 제목이 "표기 확인"이다. 칩 숫자의 합은 날짜 필터를 적용한 카드 수와 같다.
- `cd`(목록 필터의 날짜): 대표 이벤트의 카드 날짜(위 "카드 묶음과 순서"의 날짜 규칙)다. 그 날짜가 없으면(2026-10-27 결정 19절·26-3) 피드 글에서 온 카드는 최신 signals run(`signals/runs/*/signals.csv`)에서 같은 글의 게시일을 찾아 쓰고(`pub`에도 넣는다), 그것도 없으면 마지막 관측일을 쓴다. 마지막 관측일은 최신 signals run이 같은 신호(예: 계속 붙어 있는 OpenRouter 할인)를 아직 보이면 그 run의 날, 아니면 구성원 근거가 마지막으로 수집된 날이다. 그래도 정할 수 없으면 키를 넣지 않고, 필터는 이런 카드를 지난 변화로 센다.
- `ld`(묶음 카드의 마지막 관측일): 이벤트 2건 이상을 묶은 카드에만 넣는다. 구성원 이벤트의 `after.observed_at_utc`를 KST 날짜로 바꾼 값 중 가장 늦은 날이며, 변경 행에 "관측 M/D"로 보이는 날과 같은 값이다. 관측한 구성원이 하나도 없으면(공지만 있는 이벤트뿐이면) 키를 넣지 않는다. 회색 "그대로" 행과 비교 줄의 "조회" 시각은 쓰지 않는다. 필터가 `cd`와 함께 읽는 값이고, `cd`와 카드 묶음, 정렬, 날짜 표시는 바뀌지 않는다.
- `sub`
  - 조건 변경: `billing.*`는 "과금 · 캐시/Batch/단위/구간/할증", `support.*`는 "지원 · 해상도/입력 형식/지역/컨텍스트 한도/라이선스/alias" 중 키에 든 낱말로 고른다. 모르는 키는 그대로 쓴다.
  - 공급 경로 변경: `remove` 경로 중단, `add` 경로 추가.
  - 한시 할인: `period_state` `active` 진행 중, `ended` 종료(없거나 섞이면 비움).
- `flag`: 묶음에 `conflicted`가 있으면 "출처 상충", `candidate`가 있으면 "공식 확인 전", 유형 미정이면 "유형 미정: " 뒤에 후보 유형을 " 또는 "으로 이어 붙이고(예: "유형 미정: 모델 출시 또는 공급 경로 변경"), 이것들을 " · "로 잇는다.
- `sum`(목록·제목 문구)은 모델·경로·유형·날짜 사실로만 만든다. 예: "12개 항목 단가 1/1부터 인상 예정", "단가 인상 언급 · 관측값 확인 전", "경로 중단 · 날짜 미확인".
  - 인상·인하는 엔진 `change.delta` 부호가 모두 같을 때만 쓰고, 아니면 "변경"이다.
  - 관측값이 없는 가격 claim은 `claim_kind`(`price_increase`, `price_decrease`)로 정한다.

### 날짜

| 카드 | eff | effLabel |
|---|---|---|
| 한시 할인 | `dates.end_date`, 없으면 `period_end.date` | 할인 종료일 |
| 모델 출시, 경로 추가 | `dates.route_added_date` | 제공일 |
| 제공 종료, 경로 중단 | `dates.effective_from` | 제공 종료일, 경로 중단일 |
| 그 밖(예정 변경 등) | `dates.effective_from` | 적용일 |

- `YYYY-MM-DD`가 아닌 값(시각이 붙은 값 포함)은 날짜 없음으로 다룬다. 묶음에 날짜가 여럿이면 가장 이른 날짜를 쓴다.
- `period_end.basis`가 `derived_from_publication`이면 `effQual`(템플릿 "해석" 배지)에 "공지 게시일(M/D) 기준으로 연도를 해석한 날짜"를 넣는다.
- 한시 할인에 날짜가 없고 `dates.end_phrase`가 있으면 `effNote`에 원문을 넣는다(예: 원문 “for a limited time”).
- 관측으로 잡은 가격·조건 변경은 적용일이 없다(템플릿은 "미확인"). 대신 비교 조건 줄에 "관측 M/D → M/D"를 둔다.

### 바뀐 내용 표

- 열(`chgHead`)
  - 예정 변경: 항목 · 현재 · 예정 · 변동 · 적용 · 출처. 묶음의 현재가 종료일·적용일이 하나씩이면 "현재 (M/D까지)", "예정 (M/D부터)"로 쓴다.
  - 한시 할인: 항목 · 할인 전 · 할인가 · 할인율 · 기간 · 출처.
  - 나머지: 항목 · 이전 · 현재 · 변동 · 적용 · 출처.
- 항목 이름은 청구 항목(입력 토큰, 출력 토큰, 캐시 읽기, 캐시 쓰기, 그 밖은 `<item> 단가`)이고, 행마다 다른 조건(예: 등급 Batch, Standard)이 있으면 앞에 붙인다.
- 금액은 USD면 `$` 뒤에 소수 둘째 자리까지 0을 채운 값(0은 `$0`), 다른 통화는 `<금액> <통화>`다.
- 변동은 엔진 `change.delta`·`change.pct`를 그대로 써서 부호 붙은 금액과 "인상 N%"·"인하 N%"로 둔다. 이전 값이 0이라 변동률이 없으면 "무료 종료"다. 할인율은 `discount_pct_basis`가 `stated`일 때만 쓴다.
- 행 상태: confirmed `ok`, candidate `unk`, conflicted `con`.
- 상충 가격은 숫자 하나로 만들지 않고 `values_by_source`(엔진이 같은 모델·경로·항목·통화·단위·조건으로 묶은 출처별 값)를 나란히 둔다. 출처 번호는 after run 기준이다.
- 조건 변경은 조건 행(예: 캐시 읽기 배율)을 먼저 두고 그 항목의 단가 행을 잇는다. 조건 값은 엔진 표기 그대로다(예: "0.1 x base input price").
- `unchanged_items`는 회색 "그대로" 행으로 둔다.
- 값이 없으면 미확인(`{unk}`)으로 둔다(예: "현재가 미확인", "할인가 공개 안 됨"). 날짜만 있는 이벤트(경로·출시·종료, 값 없는 claim)는 행이 없다.

### 비교 조건

- 통화, 단위, 비교한 조건(등급 등, `rate_period`와 `cache_read_multiplier`는 뺀다), 경로, 공지 경로(`announced_via`가 있을 때), 조회(가장 늦은 관측 시각, KST), 관측(가격·조건 변경의 "M/D → M/D") 순이다.

### 출처

- (`source_key`, `run_id`)마다 하나씩 `s1`, `s2` … 순서로 번호를 매긴다. 피드는 글(근거의 `locator`가 `feed/…`)마다 따로 매겨서, 칩마다 그 공지의 링크와 게시일이 보인다(2026-10-27 결정 20절). 전에는 run 하나에 칩 하나라 Vercel 공지 카드 21장이 칩 하나를 나눠 써서 대부분 카드에서 다른 공지의 날짜와 링크가 보였다.
- 이름: 공급사 공식(`manufacturer_official`)은 모델 제조사, 채널 공식(`channel_official`)은 경로 게시자, 신호 출처는 그 게시자 이름을 쓰고 뒤에 ` · <source_key>`를 붙인다. 그 밖은 `source_key`만 쓴다.
- 배지: 공급사 공식 `sup`, 채널 공식 `ch`, 그 밖은 외부 출처 `ext`. authority는 이벤트 `sources`에 있으면 그 값을, 없으면 `catalog.authority()`를 쓴다.
- 시각: 게시일(근거가 한 출처인 이벤트, 공지의 UTC 날짜), 조회(관측 시각) 또는 수집(run id 시각). 조회·수집 시각은 KST다.
  - 게시일이 이벤트에 없으면 최신 signals run에서 찾는다(`feed_days`): `signals.csv`의 `published_at_utc`, 그리고 같은 run의 원본 피드(`signal_sources.csv`의 `raw_path`)를 수집기 파서(`atom_entries`, `rss_entries`)로 읽은 글 날짜다. 피드의 `<published>`가 없으면 `<updated>`를 쓰는데, Vercel 공지 4건을 열어 보니 `<updated>`가 페이지의 게시일(datePublished)과 같았고 나중 수정 시각과는 달랐다. modelpricewatch는 항목 id에 같은 날짜가 들어 있다.
- 링크는 http(s) URL일 때만 넣는다.
- 인용(`ev`): claim은 `sources.quote`, 없으면 `locator`. 관측은 비교한 두 관측의 locator를 "이전/현재"(예정 변경은 "현재가/예정가")로 붙인다.

### 렛서 관계 (`--internal-routes`)

- 카드의 렛서 관계(`relKey`, `relShort`, `relDemo`)는 `--internal-routes` 파일로만 정한다. 엔진 `letsur_usage`는 지금 항상 `unknown`이라 쓰지 않는다. 옵션이 없으면 모든 카드가 `relKey: "unk"`, `relShort: "사용 경로 확인 필요"`, `relDemo: false`다(옵션이 생기기 전과 같은 결과).
- 파일 형식: `{"is_demo": true 또는 false, "records": [{"model_id": "...", "route_id": "..." 또는 null, "endpoint_id": "..." 또는 null, "basis": "settings" 또는 "observed" 또는 없음}, ...]}`. `endpoint_id`와 `basis`는 빠져도 된다. 그 밖의 키(`purpose`, `basis_note` 등)는 읽지 않는다.
- `basis: "settings"`(2026-10-28 박건 결정): 렛서 QnA 답변(9/23) 질문 2의 '설정에 등록된 공급 경로'다. 렛서는 설정에 경로가 있어도 실제 트래픽이 흐르는지는 따로 확인해야 한다고 했다. 이 근거의 카드는 `relDemo: false`, `relSet: true`이고 `relShort` 끝에 " (렛서 설정)"이 붙는다(`route_basis`). 화면은 적용 배지에 "· 설정", 상세 "현재 사용 경로"에 '렛서 설정' 태그, 제안 근거에 "(렛서 관계는 9/23 답변의 렛서 설정 경로 기준, 실제 트래픽 미확인)"을 붙인다.
- `basis: "observed"`(2026-10-28 박건 결정): 같은 날 렛서 API를 모델마다 한 번 호출해 응답 헤더·필드로 판별한, 그 호출이 실제로 지나간 경로다. 그 경로를 쓰고 있다는 확인일 뿐 다른 경로를 쓰지 않는다는 뜻은 아니다. 이 근거의 카드는 `relDemo: false`이고 `relSet`도 없으며 `relShort` 끝에 " (호출 확인)"만 붙는다. 화면의 배지·태그·제안 근거 문구는 settings에만 있어 observed에는 나오지 않는다.
- 끝 표시를 정하는 레코드(`route_basis`): 카드 경로에 그 모델의 레코드가 있으면 그 레코드의 근거, 없으면(`other`·`none`) 그 모델 레코드 전체의 근거다. 모두 settings면 " (렛서 설정)", 모두 observed면 " (호출 확인)", 섞이면 " (렛서 설정·호출 확인)"이고 이때는 `relSet`이 없다. 예: gpt-6-astra는 OpenAI 직접 카드가 "(렛서 설정)", Azure 카드가 "(호출 확인)", 그 밖의 경로 카드가 "(렛서 설정·호출 확인)"이다. 할인 끝남 주의 줄(`risk`)의 짧은 표기("렛서 설정 경로", "렛서 호출 확인 경로")는 그 줄이 말하는 경로의 레코드를 따른다.
- 한 모델에 basis가 없는 레코드가 하나라도 있으면 그 모델 전체를 `is_demo`로 본다(아래).
- 카드의 모델(대표 이벤트 `model_id`)로 레코드를 찾고 카드 경로(대표 이벤트 `route`)와 `route_id`를 비교한다.

| 그 모델의 레코드 | relKey | relShort |
|---|---|---|
| 카드 경로와 같은 `route_id`가 있음 | `use` | 이 경로로 사용 중 |
| `route_id`가 다른 경로뿐 | `other` | 모델 제공 중 : <쓰는 경로> 경로로 사용 |
| `route_id`가 모두 null | `none` | 미도입 |
| 레코드 없음 | `unk` | 사용 경로 확인 필요 |

- 레코드가 없는 모델은 미사용이 아니라 미확인이라 `unk`로 둔다.
- 한 모델에 레코드가 여럿이면 카드 경로와 같은 레코드가 하나라도 있을 때 `use`, 없고 null이 아닌 경로가 있으면 `other`(쓰는 경로를 모두 ", "로 잇는다), 모두 null이면 `none`이다.
- `other`의 쓰는 경로는 카드 경로와 같은 표기(게시자 · route_id, 예: "Vercel · vercel_ai_gateway")다. 경로 표기가 없는 카드도 그 모델에 경로가 있는 레코드가 있으면 `other`다.
- `endpoint_id`는 경로가 같을 때만 보조 정보로 붙인다(예: "이 경로로 사용 중 : endpoint fal-ai/veo3.1", 여럿이면 ", "로 잇는다). 카드는 endpoint를 비교하지 않아 1011 원본 예시의 "이 endpoint로 사용 중"은 쓰지 않는다.
- `is_demo`
  - true: basis가 없는 레코드가 있는 모델의 카드(`use`, `other`, `none`)에 `relDemo: true`를 넣고 `relShort` 끝에 " (가정)"을 붙인다. 템플릿은 제안 근거 끝에 "(렛서 관계는 시연용 가정)"을, 상세 "현재 사용 경로"에 가정 태그를 붙인다. 영향 줄 "제공·사용"은 태그 없이 `relShort`만 보여서 " (가정)"을 문구에 넣었다(1011 원본 표기와 같다). 모든 레코드에 basis가 있으면 true여도 아무것도 붙지 않는다.
  - false: 둘 다 붙이지 않는다(basis가 없는 레코드는 표시 없이 사실처럼 보이니 레코드마다 basis를 단다). 레코드가 없는 카드(`unk`)는 is_demo와 상관없이 `relDemo: false`다.
  - 공급사 비교 표(`compare.py`)에서 모델의 첫 레코드 경로 행에 붙는 칩은 basis를 보지 않고 true면 "가정", false면 "사용 경로"다.
- 제안·다음 할 일은 템플릿 규칙이 `relKey`로 계산하고, 이 규칙은 바꾸지 않았다. 예: `other`인 단가 인상 예정 카드는 "기존 조건 유지 검토", "현재 경로 유지 : Google · google_direct 새 단가는 비교용으로 기록"이다. `unk` 카드는 사용 중으로 가정하되 "확인 후 "와 "먼저 렛서 사용 경로 확인"이 붙는다.
- 모델별 사용 경로(`MODELS[model].use`)는 카드 경로와 상관없이 모델 단위로 같은 파일에서 채운다(2026-10-21 박건 요청). 카드에 나온 모델만 다룬다.
- 이 값은 지금 화면에 나오지 않는다. 이 값을 보일 템플릿의 "모델별 현황" 표(`renderModels()`, 1037행)는 정의만 있고 호출되지 않으며, 표를 넣을 `id="models"` 요소도 없다. 1011 원본도 같다(1221행에 정의, 호출 없음). 아래 규칙은 페이지 데이터 기준이다.

| 그 모델의 레코드 | use |
|---|---|
| null이 아닌 `route_id`가 있음 | <쓰는 경로> 경로로 사용 |
| `route_id`가 모두 null | 미도입 |
| 레코드 없음 | 넣지 않음(표를 그리면 템플릿 기본값 "사용 경로 미확인") |

- `use`의 쓰는 경로는 카드 `other`와 같은 표기(게시자 · route_id)를 ", "로 잇는다. 카드 `other` 문구에서 "모델 제공 중 : "만 뺀 꼴이다. 예: "Vercel · vercel_ai_gateway 경로로 사용".

### 상세페이지 필드 (박기범, 2026-10-26)

상세 화면이 종류별로 다르게 그리도록 엔진이 이미 쓴 사실을 카드에 더 넘긴다. 판단 문구는 만들지 않는다.

- `st`: 묶음 상태. `conflicted`가 하나라도 있으면 conflicted, 모두 confirmed면 confirmed, 나머지는 candidate. 템플릿은 "확정 / 공식 확인 전 / 출처 상충" 배지로 쓴다.
- `chk`: `[구분, 문구]` 목록. 이벤트 `gaps`의 `check_first`는 `first`, `limits_value`는 `limit`, `next_checks`는 `next`다. 문구는 `GAP_KO`·`NEXT_KO`의 한국어이고, 없는 field는 엔진 `reason`을 그대로 쓴다. `letsur_usage`는 모든 카드에 같아 뺀다(현재 사용 경로 칸이 같은 말을 한다).
- `tc`: 유형 미정 카드의 후보 유형 이름(예: 모델 출시, 공급 경로 변경). 있으면 배지는 "유형 미정"과 후보를 따로 보여 준다.
- `clue`: 관측값·공지 가격·할인율이 하나도 없는 카드. 가격·할인·예정·조건 카드에서 템플릿은 단서 상자(원문, 확정하려면)를 보여 주고 원가는 "판단 전", 제안은 "판단 보류"다.
- `ps`: 한시 할인 `period_state`(묶음에서 하나일 때). `pub`: 대표 이벤트의 공지일.
- `n`: `[바뀐 행 수, 그대로 행 수]`. `cg`: 행마다 `[조건 묶음, 항목]`. 조건 묶음은 행마다 다른 조건 값을 " · "로 이은 것이고 `context_length`는 "컨텍스트 1M"처럼 쓴다. `chg[0]`은 이전처럼 묶음과 항목을 이은 이름이다.
- 바뀐 내용 표의 같은 조건·항목·값 행은 하나로 합친다(같은 값을 다른 run이나 출처에서 다시 읽은 경우).
- 비교 조건 줄의 엔드포인트 조건은 한국어 이름(컨텍스트, 엔드포인트, 정밀도, 제공자 등)으로, `context_length` 값은 1M·256K로 쓴다.

템플릿 상세 화면(목록·달력·그래프는 그대로):
- 핵심 변화: 가격 변경은 "N개 항목 인하 · 범위" 한 줄과 폭이 큰 3개 막대, 예정 변경은 모든 항목의 변동이 같으면 한 줄, 한시 할인은 진행·종료와 공지일, 조건·가격 변경은 조건 행과 단가 행, 경로 추가는 제공일과 유형 미정 안내. 아래에 `chk` 목록.
- 바뀐 내용: 바뀐 행만 조건 묶음 제목 아래에 펼치고, 그대로 행은 "그대로인 항목 N개 보기"로 접는다.
- 원가 칩: 항목 이름을 잇지 않고 "원가 ▼ 최대 N% · N개 항목". 렛서에 주는 영향의 원가 줄은 항목이 3개를 넘으면 요약 한 줄.
- 제안: 단서만이면 판단 보류, 확정 전(candidate·conflicted)이면 고객 할인을 보류, 끝난 할인은 기존 조건 유지("지금 단가가 할인 전으로 돌아왔는지 확인"), 경로 추가·모델 출시는 할인이 아니라 경로 비교·도입 후보, 할인율을 모르는 할인은 판단 보류.

### 메인페이지 정규화 (김연우 규칙, 박기범 합침, 2026-10-27)

"확인"에는 엔진의 다음 수집 확인(`next`)도 들어간다. 굵은 첫 줄(예: "현재 경로 유지 : Google · google_direct 새 단가는 비교용으로 기록", "고객 할인 : 할인 기간에만 한정해 검토, 판매가 기본값은 유지")과 "현재 사용 경로"(예: "모델 제공 중 : Vercel · vercel_ai_gateway 경로로 사용 (가정)")도 같은 꼴이다. "Vercel · vercel_ai_gateway"처럼 경로 이름 안의 "·"는 그대로다.

- 되돌아간 가격(2026-10-28, 결정 기록 29절 렛서 답변: 원래 가격으로 돌아온 건은 지금도 바뀐 것처럼 보이지 않게, build.py `reverted`·`mark_reverted`): 관측된 가격 변화(`price_change`)를 계열(모델, 경로, 출처, 청구 항목, 비교 조건)마다 관측 순으로 보고, 그 뒤 계열의 마지막 값이 이 변화의 이전 값과 같으면 되돌아간 변화다. 계열의 마지막 변화와 다른 값으로 다시 바뀐 변화는 되돌아간 것이 아니다. 카드에 `rv`(되돌아간 가격 수)와 `rn`(바뀐 가격 수)을 적고, 모두 되돌아가면 '해소됨'으로 template `actionKey`와 build.py `judge()`가 함께 RECORD로 둔다(둘을 같이 고친다). 일부면 '일부 해소 rv/rn' 칩과 상세 한 줄만 붙는다. 변동 잦음 묶음 줄에는 되돌아간 가격이 있는 카드 수('되돌아감 N')를 붙인다. 10/27 자료: 되돌아간 변화 14건이 OpenRouter 카드 8장에 흩어져 있고, 모두 되돌아간 카드는 없다.
- 목록 정렬: 추천 순(기본, 렛서 판단 단계 → 급한 순 → Suggested Action), 적용일 순(급한 순 → Suggested Action), 유형별(이전 화면의 종류 묶음). 유형 칩과 "지난 변화 보기" 거르기는 그대로 겹친다. 처음 열 때 고르는 카드도 추천 순 맨 위 카드다.
- 렛서 판단 단계(2026-10-28 가안, template.html `tierOf`): 3팀 서면보고에 적힌 렛서 판단 순서(지금 쓰는 판매처 → 판매 중단 위험과 기한 → 같은 조건의 비용 증감 → 대신 쓸 판매처 → 보안·계약상 빼야 할 곳)를 따른다. 렛서 경로(APPLIES)의 판매 중단(제공 종료, 경로 중단) → 렛서 경로의 비용 증감(가격 변경, 예정 변경, 한시 할인, 조건·가격 변경) → 렛서 경로의 그 밖 → 사용 경로 모름(UNKNOWN) → 다른 경로의 대신 쓸 만한 변화(`dirOf`가 good: 인하, 할인, 경로 추가) → 다른 경로의 그 밖 → 렛서가 쓰지 않는 모델 → RECORD 순이다. 렛서 답변 원문은 확인 전이고, 보안·계약 기준은 렛서 신뢰 공급사 목록이 없어 비워 두었다. 10/27 자료 기본 목록 19장에서는 gemini-3.8-flash Vercel 할인 카드(APPLIES)가 4번째에서 1번째로 오르고, 다른 경로의 인상 카드 2장이 인하 카드 뒤로 간다.
- 달력 날짜: 카드 하나가 날짜 여러 개를 낼 수 있다.
  - 적용(`effective`): `eff`. 한시 할인·제공 종료·경로 중단의 `eff`는 종료(`end`)로 표시한다.
  - 예정 변경은 `eff` 전날을 "현재 단가 마지막 날"(종료, 해석 날짜 점선)로 더한다.
  - 다음 확인(`next_check`, 팀 기준 날짜이고 공지 날짜가 아님): `eff`가 미래이고 `chk`에 먼저 확인(`first`)이 있으면 전날 "적용 전 확인"(종료 날짜면 "종료 전 확인"), 다음 수집 확인(`next`)만 있으면 다음 날 "적용 후 재관측"("종료 후 재관측").
  - "14일 내 일정" 수는 14일 안에 날짜가 있는 카드 수다.
- 단가 추이 비교 모드: 엄격 비교(기본)는 `ref` 선을 빼고, 전체 관측은 모두 보인다. 뺀 선 이름은 "출처·설명"에 적는다. 남는 선이 없으면 참고 선을 그대로 보이고 그렇다고 적는다. 비교 조건 줄은 모델 · 항목 · 단위(`units`) · 가격 조건(탭)이다.
  - `ref`(2026-10-27 결정 26-2): 조건이 정해지지 않은 선만이다. 모델 단위 표시 가격(`price_basis`가 `DISPLAY_BASIS`, 예: "displayed model quote", "starting listing quote")과 공급사 비교 표가 상태로 비교에서 빼는 엔드포인트(`endpoint_status`가 0이 아님. OpenRouter의 -1·-2는 비교 표처럼 비교한다)가 해당한다. 게이트웨이 엔드포인트 선은 탭이 정밀도·지역·등급까지 나뉘므로 공급처가 달라도 비교한다. 참고 선은 단위가 같고 그 선이 적은 조건을 모두 갖춘 탭에도 붙고, 자기 탭에 다른 선이 없으면 그 탭은 없앤다.
  - 탭 이름(2026-10-27 박건 요청: 탭 줄이 화면 밖으로 넘침): 범위 메모 조건(`TAB_QUIET`: 통화 안내, 입력 형식, Commercial Regions, rate_period)은 빼고, 긴 원문은 짧게 쓴다(`tab_value()`: '입력 272K 이하', '캐시 30분', '272K 초과 요청 입력 2배·출력 1.5배'). 원문 그대로의 조건은 `conds`로 넘겨 그래프 위 '비교 조건' 줄과 탭 마우스 설명에 보인다. 탭 줄은 패널 폭에서 줄바꿈된다.
  - `old`: 가장 최근 수집(그 모델 선들의 가장 늦은 run)에 없는 선. 템플릿의 "그래프 안 최저"(옛 "현재 최저") 칸은 이 선을 세지 않는다(결정 9절·21절).
  - `units`: 탭이 둘 이상일 때 탭 이름별 단위.

### 비우는 필드

- `act: "pending"`(평가 보류).
- 넣지 않는 필드: `head`, `key`, `keyAdd`, `chip`, `what`, `checkFirst`, `notes`, `extra`, `alt`, `imp_rows`, `dir`, 캘린더 문구(`cal`). 엔진 `significance`·`impact`·`suggestion` 문구도 쓰지 않는다.
- 원가 칩과 제안 문구는 템플릿 로직이 바뀐 내용 표 값으로 계산한다.
- `link`·`risk`·`postEst`(2026-10-27 결정 1번 가안): 게이트웨이 할인이 상류 공급사의 공식 예정 가격으로 끝날 때만 채운다(공급사 비교 표의 16절 맞춤과 같은 조건). 예정 변경 카드와 할인 카드가 '함께 볼 이벤트'로 서로 잇는다(`link`). 렛서 경로의 할인 카드에는 할인 끝난 뒤 추정 가격(`postEst`, 핵심 변화에 표시)과 주의 줄(`risk`)이, 예정 변경 카드에는 렛서 경로도 같은 가격이 될 수 있다는 주의 줄이 붙는다. `build.py` `link_promotions()`가 `compare.py` 표의 `promo`를 읽고 페이지에 넣기 전에 지운다. 10/27 데이터에서는 gemini-3.8-flash의 네 카드(Google 인상, Vertex 인상, Vercel 할인, OpenRouter 할인)만 해당한다.

### MODELS, COLLECTED

- `MODELS`: 카드에 나온 모델마다 제조사(`catalog.maker()`, 모르면 빈칸)와 종류(`MODEL_MODALITIES`: LLM, 영상, 이미지). 사용 경로(`use`)는 `--internal-routes` 파일에 그 모델의 레코드가 있을 때만 채운다(위 "렛서 관계"). 템플릿은 `MODELS`를 호출되지 않는 `renderModels()`에서만 읽어서 `MODELS`는 지금 화면에 나오지 않는다.
- `COLLECTED.runs`: `report.json` `processed_runs`의 [run 시작 시각(KST, run id에서 읽음), run id], 오래된 순. 템플릿은 상단 요약의 수집 횟수와 기간에 쓴다. 원본의 "수집 데이터 전체" 표(`COLLECTED.models`)는 페이지를 열 때 호출되지 않는 코드라 채우지 않는다.

### 단가 추이 (모델별 가격 화면의 '가격 추이')

- 화면 탭(2026-10-28 박건 결정): 머리줄에 '변화 | 모델별 가격' 탭이 있다(`setPage`, `body[data-page]`). 변화 화면은 요약, 일정 캘린더(전체 폭), 목록과 상세다. 모델별 가격 화면은 왼쪽 모델 목록, 오른쪽 위 '가격 추이'(이 절의 그래프), 그 아래 '현재 가격 표'(공급사 비교 표)다. 캘린더 옆에 붙어 있던 단가 추이 칸에 표를 넣으니 칸이 길어지고 폭이 모자라서 화면을 나눴다.
- 수집 상태 화면(2026-10-28 박건 제안, 결정 기록 29절 렛서 답변: 수집 실패는 '변화 없음'과 구분하고 아침에 먼저 보이게, build.py `health`, 슬롯 `HEALTH`): 머리줄 세 번째 탭('변화 | 모델별 가격 | 수집 상태', 주소 `#health`). 마지막 수집 시각과 출처 수(정상·실패)는 가장 최근 처리된 run의 sources.csv(`fetch_status`·`parse_status`·`error`·`requested_url`)에서 읽는다. '지금 실패 중'은 그 run에서 실패한 출처이고, 실패가 시작된 run은 state.json gaps의 `source_failed`(run마다 한 건, `active` 표시는 갱신되지 않아 쓰지 않음)를 processed_runs 순서로 거슬러 이어진 실패 run의 처음이다. '최근 14일 실패 기록'은 지금은 실패하지 않는 출처의 실패 run 수와 기간이고, 최신 run에 있으면 '정상으로 돌아옴', 없으면 '등록부에서 빠짐'이다. '원문 재검증 필요'는 gaps `parser_fingerprint_mismatch`의 출처별 건수, '등록부 점검 후보'는 최근 7일과 앞으로 일정이 있는 제공 종료·모델 출시·공급 경로 변경 카드다. 변화 화면은 수집 현황 타일 아랫줄에 '실패 N곳'을 붙이고, 실패가 있으면 맨 위에 안내 줄과 수집 상태 바로 가기를 둔다. 모델별 가격은 그 모델의 출처가 실패 중이면 그래프 위에 '이어진 선은 변화 없음이 아님'을 적는다. 10/27 자료: 출처 158곳 모두 정상, 최근 실패 9곳(fal·BytePlus Seedance는 정상으로 돌아옴, Google Veo 3곳은 등록부에서 빠짐), 원문 재검증 4곳(OpenRouter 엔드포인트).
- 모델 목록은 만든 회사별로 묶는다(`MAKERS`: 모델 id 앞부분으로 Anthropic·ByteDance·DeepSeek·Google·Moonshot AI·OpenAI·Z.AI, 그 밖은 '기타'). 회사와 모델은 이름순이고(숫자는 크기순), 처음 고른 모델은 목록 맨 위다.
- 주소: 변화는 `#카드id`·`#v_묶음`, 모델별 가격은 `#m/모델`이다. 카드 상세의 '가격 추이 보기'·'공급사 비교 표 보기'는 그 모델을 고른 모델별 가격 화면의 해당 칸으로 간다. 그래프의 점을 누르면 변화 화면의 그 카드로 간다.
- 이벤트 카드가 있는 모델만 넣는다(키 `model_id`).
- 탭은 공급사 비교 표와 같은 묶음(정밀도 묶음 · 지역 · 등급, 그 밖의 가격 조건 + 단위)이고, 선은 경로와 게이트웨이 엔드포인트, 측정은 청구 항목이다(2026-10-27 결정 21절).
  - 게이트웨이(OpenRouter, Vercel) 목록이 적는 엔드포인트 사실(`endpoint_tag`, `endpoint_provider`, `endpoint_model_slug`, `context_length`, `quantization`, `endpoint_status`, `endpoint_discount`, `discount_application`)과 가격 근거 표기(`price_basis`, 모델 페이지 수집기도 낸다)는 그대로는 탭을 가르지 않고 선을 가른다. 다만 `quantization`의 정밀도 묶음(mxfp4·nvfp4는 fp4, mxfp8은 fp8)과 `endpoint_tag`·`region`의 지역(us·us-east-1은 US, eu·eu-west-1·europe은 EU, global은 지역 없음)은 탭을 가른다(`tab_facts`). `service_tier`나 `prompt_tokens` 같은 실제 가격 조건이나 단위가 다르면 탭이 갈라진다.
  - 탭 이름은 정밀도 · 지역 · 그 밖의 조건 · 등급 순이고(예: "fp4 · Standard", "fp8 · US", "fp8 · US · Priority"), 지역 탭은 Standard를 적지 않는다. 값은 26-1대로 원문이고 등급과 지역만 이름(Standard·Priority, US·EU)으로 적는다.
  - 선 이름은 경로 뒤에 엔드포인트 이름(OpenRouter는 태그, Vercel은 제공자)과 양자화를 붙인다(이름에 양자화가 이미 있으면 한 번만). 그래도 같은 이름이 되는 선은 source_key 등으로 구분한다.
- 점은 실제 관측값과 공지된 예정 단가만 쓴다.
  - 관측: `state.json` `series`의 최신 관측과 이벤트의 이전·이후 관측. run마다 점 하나이고, 그 run에 없는 항목은 앞 값을 잇는다.
  - 예정: `scheduled_change`의 적용일에 예정 값을 점선으로 잇는다. 마지막 관측 뒤이고 그 선에서 관측된 모든 항목에 예정 값이 있을 때만 그리고, 아니면 날짜 메모로 돌린다.
- 빼는 것: USD가 아닌 값, 엔진 gaps에서 의심된 관측(`parser_artifact`, `csv_raw_mismatch`, `parser_fingerprint_mismatch`), claim. USD가 아닌 값과 의심 관측의 건수는 추이 설명(`note`)에 적는다.
- 탭마다 선은 6개까지다(템플릿 색 s1~s6). 이벤트가 있는 선을 먼저 남기고, 뺀 선의 개수와 이름은 설명에 적는다("선이 6개를 넘어 뺀 선 N개: ...").
- 예정 점을 그리지 않은 선은 마지막 관측의 `effective_until`(하나일 때)까지만 그린다.

## 실패·경고 표시

- 아래 경우에는 카드 없이 "오늘 생성 실패" 배너와 이유를 보인다(exit 0). 어제 화면이 최신처럼 남지 않도록 실패 화면도 그대로 배포한다. 수집 run 목록은 `report.json`을 읽을 수 있으면 채운다.

  - `report.json` `status`가 `ok`가 아님(예: 엔진 `rejected`, errors를 적는다)

## workflow (`.github/workflows/market-collection.yml`)

기존 단계·cron·permissions·concurrency는 그대로 두고 `collect` 잡 끝에 2단계를, 그 뒤에 `deploy` 잡을 더했다(박건 승인 2026-10-20). 배포 대상은 2026-10-22에 Cloudflare Pages에서 같은 저장소의 GitHub Pages로 바꿨다(저장소 공개는 박건 결정).

1. `Build dashboard`(`if: always()`): 위 실행 명령에 `--internal-routes samples/market_collection/demo_internal_routes.json`을 붙인다(2026-10-21 박건 요청). 배포 페이지의 렛서 관계는 파일의 근거대로 "(렛서 설정)"·"(호출 확인)"으로 표시된다(2026-10-28 전에는 시연용 가정이라 "(가정)"이었다). 앞 단계가 실패해도 실패 화면을 만든다.
2. `Upload Pages artifact`(`if: always()`이고 `dashboard-site/index.html`이 있을 때): `actions/upload-pages-artifact` v5.0.0(커밋 `fc324d3547104276b827a68afc52ff2a11cc49c9`로 고정, 2026-04-10 릴리스)으로 `dashboard-site`를 artifact `github-pages`(1일 보관)로 올린다. 이 단계 결과(`steps.pages.outcome`)가 `collect` 잡 output `dashboard`다.
3. `deploy` 잡(`needs: collect`, `if: always() && needs.collect.outputs.dashboard == 'success'`): `actions/deploy-pages` v5.0.1(커밋 `368f82528645a54fb793d4d04e342629a3f51346`로 고정, 2026-09-01 릴리스)으로 배포한다. 잡 권한은 `pages: write`, `id-token: write`이고 환경은 `github-pages`(배포 주소를 환경 url로 보인다)다.

- 최상위 permissions(`contents: read`, `actions: read`)는 그대로다. 잡에 permissions를 쓰면 그 잡은 최상위 값 대신 자기 값만 쓰므로 Pages 권한은 `deploy` 잡에만 있다.
- 수집·요약 단계가 실패해도 페이지가 있으면 배포한다. 페이지가 없으면 업로드 단계와 `deploy` 잡을 건너뛰고 실패를 더하지 않는다.
- 페이지 파일은 Pages artifact `github-pages`(`artifact.tar`)에 1일 남는다. 같은 파일을 올리던 `Upload dashboard` artifact(`dashboard-<run_id>-<run_attempt>`)는 뺐다.
- Pages 소스가 GitHub Actions라 Jekyll 처리가 없어 `.nojekyll`은 필요 없다. secrets도 쓰지 않는다.
- 주의
  - 배포를 허용한 브랜치(아래 체크리스트 3) 어디서 돌려도 같은 주소에 배포되고 마지막 배포가 남는다. 임시 PR 브랜치에서 `workflow_dispatch`로 돌리면 다음 배포 전까지 그 결과가 보인다.
  - 허용하지 않은 브랜치에서 돌리면 `deploy` 잡이 환경 보호 규칙에 막혀 실패한다(GitHub 환경 규칙, 이 저장소에서 실행해 보지 않음).
  - 배포가 실패하면 `deploy` 잡이 실패해 run도 실패한다.
  - 생성 단계가 exit 1이어도 실패 화면이 배포된다(run은 실패로 남는다).
